# cc-connect 能力边界实测

> 测试时间：2026-09-15 01:00–01:10
> 测试目的：确认「能否让某条微信消息只投递给指定的 agent」
> 结论：**不能**，除非改架构。以下是完整证据。

---

## 一、被验证的假设

用户侧的现象是：「我 `@dsh`，实际上其他 agent 也能收到我的消息，他们也会回复，只是发不出来。」

这个描述**方向正确，但机制不同**。需要修正的是「被过滤」发生的位置 —— 不在入口，在出口。

---

## 二、消息扇出（实测）

### 证据：同一条消息，N 次投递

用户发出一条测试消息后，日志记录：

```log
01:05:19.746 message received  msg_id=7505310717695579528 content_len=24
01:05:20.725 message received  msg_id=7505310717695579528 content_len=24
01:05:20.780 message received  msg_id=7505310717695579528 content_len=24

01:05:29.693 turn complete  agent_session=e065d124…  tools=0 response_len=301 silent=false
01:05:40.858 turn complete  agent_session=2337a071…  tools=2 response_len=233 silent=false
01:05:50.514 turn complete  agent_session=e5f72d2e…  tools=2 response_len=125 silent=false
```

**三个 agent 全部收到、全部跑完、全部产生回复。**

（同一条 `msg_id` 出现在 3 条 `message received` 里，正是「扇出」的直接证据；此前另一条 12 字消息也观察到同样模式。）

### 这意味着

- 每条用户消息 = **N 次完整 LLM 调用**（N = 挂微信的 project 数）
- 静默机制只挡住「消息位」，**挡不住 token 消耗**

---

## 三、`NO_REPLY` 的真实身份

### 它不是桥接的内置开关

在 `cc-connect.exe`（约 23MB 的 Go 二进制）中检索 `NO_REPLY` 字面量：**零命中**。

对比：检索 `banned_words` 有 2 处命中（反射元数据 + 内置文档字符串）。

### 它是提示词约定

工作链路：

1. agent 的规则文件（`CLAUDE.md` / `AGENTS.md`）里写着「不该你答时，整段只输出 `NO_REPLY`」
2. agent 读消息 → 自己判断「不是找我」→ 输出 `NO_REPLY`
3. 桥接按正则 `(?i)^\s*NO_REPLY\s*$` 匹配整段回复 → 命中则标记 `silent=true`、不投递

**关键推论**：既然判定依据是「整段恰好等于 NO_REPLY」，那么任何附加文字都会让静默失效 —— 这正是「思考过程泄漏」会破坏点名制的原因（详见 `01-思考泄漏与共享记忆层-诊断修复报告.md`）。

## 四、`banned_words` 定向拦截实验（失败）

### 官方语义

配置样例中的原文：

> Messages containing any of these words will be blocked and NOT forwarded to the AI agent. Matching is case-insensitive.
> 消息中包含以下任一违禁词时，将被拦截，不会转发给 AI Agent。匹配不区分大小写。

语义看起来正是「入站拦截」，如果它能按 project 生效，就比 `NO_REPLY` 高一个档次（消息根本不进 agent）。

### 实验设计

由于**无法从二进制确定该字段的配置层级**（`banned_words` 在 exe 里只出现 2 次：一次是反射元数据，同 struct 字段群为 `MaxMessages` / `ReplyFooter` / `*OutgoingRateLimitConfig` / `TimeoutSecs` / `SessionMode` / `BannedWords`；一次是配置文件注释原文，不含归属信息），采用「两个候选层级各写一份」的策略：

```toml
# 候选层级 ①：项目级（与 name 同级）
[[projects]]
name = "my-workbuddy"
banned_words = ["BANTEST0915"]

# 候选层级 ②：平台级（与 allow_from 同层）
[projects.platforms.options]
allow_from = "<YOUR_OPENID>@im.wechat"
banned_words = ["BANTEST0915"]
```

两个位置都只配给 `my-workbuddy`，其余两个 project 不配。然后让用户发一条**不带 @ 前缀**的消息（这样三个 agent 默认都会应答，缺席的那个即被拦截的目标）。

### 结果：两处都无效

日志显示三个 agent 照常全部处理、全部回复（见第二节的日志），`my-workbuddy` **没有任何被拦截的迹象**。

### 结论

- 该字段极可能是**全局**配置（写在 project / platform 内被 TOML 库静默忽略 —— pelletier 默认不对未知字段报错，所以既不生效也不报错）
- 全局拦截 = 拦掉所有 project，**无法实现「只让某个 agent 收到」**
- 未去验证「全局」假设：证实或证伪都指向「对本需求不可用」，无决策价值

### 经验

> **当配置项的层级无法从文档确定时，「多个候选位置各写一份」的策略可以一次实验同时覆盖多种可能。** 前提是该配置库对未知字段静默忽略（pelletier / TOML 默认行为），否则会启动失败 —— 而启动失败本身也是有效结论。

## 五、微信私聊没有「@ 语义」

### 本机形态

会话键固定为 `weixin:dm:<openid>@im.wechat` —— **私聊**，不是群聊。

在私聊里，`@dsh` 对桥接而言就是若干个普通字符，**没有任何结构化 @ 数据**可用于路由。

### 对比：飞书侧才有原生 @ 能力

二进制中，以下字段紧邻出现（属于飞书平台实现）：

```
require_mention  /feishu/webhook  p2p_chat_create  reply_in_thread
<at id=%s></at>  receive_id_type  ...
```

- `require_mention` —— 「必须 @ 我才响应」
- `<at id=%s></at>` —— 结构化的 @ 标签（可解析出被 @ 的是谁）

**微信侧没有对应实现。**

### 微信平台实际有的字段

`allow_from` —— 但它的语义是「**谁**可以给这个 project 发消息」（按**发送者**过滤），不是「消息里 @ 了谁」。

## 六、变通用法：把 `allow_from` 当入站开关

既然 `allow_from` 是按发送者过滤的白名单，那么把它设成一个**不存在的用户 ID**，就等于给该 project 装了一个「入站总开关（关）」：

```toml
[projects.platforms.options]
allow_from = "disabled"   # 谁都不匹配 → 该 project 收不到任何微信消息
```

**为什么这个用法有价值**：`relay`（agent 之间的跨项目拨号）走的是 cc-connect **内部通道，不经过微信平台** —— 所以被关掉入场的 agent 依然能被其他 agent 叫醒干活，只是不再直接从微信收消息。

**适用**：让某几个 agent 不再插话（「平时只跟一个 agent 对话」）。
**不适用**：按 @ 动态切换（白名单是静态的，不看你消息内容）。

---

## 七、`[[hooks]]` 不能用于路由

`[[hooks]]` 支持事件 `message.received` / `message.sent` / `session.started` / `cron.triggered` / `error` 等，上下文通过 `CC_HOOK_*` 环境变量传入（二进制中可见 `CC-Connect-Hooks/1.0`、`CC_HOOK_SESSION_KEY=`）。

但在整个二进制里检索不到任何可阻断的语义（`hook_block` / `blocked_by_hook` / 拒绝码之类）。

**结论：它是只读观察者，只能事后转发，不能拦截或改写消息。**

---

## 八、想要「定向投递」的三条可行路线

| 路线 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **独立 bot 身份** | 每个 agent 配各自的微信机器人 token | 路由发生在微信服务端，最彻底 | 微信里多 N 个联系人 |
| **自建聊天入口** | 用 management API（`POST /api/v1/projects/{name}/send`）按 project 定向投递 | 天然定向，可自定义 UI | 需要开发 |
| **单前台 + relay** | 微信只挂一个 project 当前台，由它判断该转给谁、再用 relay 转发 | 零开发，能省掉 N-1 次 LLM 调用 | 延迟大（relay 往返实测 46–51 秒）、单点 |

## 附：本次实验用到的命令

```bash
# 查配置里各 project 的生效字段（比肉眼翻 TOML 可靠）
python -c "import tomllib;d=tomllib.load(open(r'$HOME/.cc-connect/config.toml','rb'));
[print(p['name'], p.get('banned_words'), [x['options'].get('banned_words') for x in p['platforms']]) for p in d['projects']]"

grep "message received" ~/.cc-connect/logs/cc-connect.log | tail -20

# 看每个 project 是否真的跑完、是否静默
grep "turn complete" ~/.cc-connect/logs/cc-connect.log | tail -20
```
