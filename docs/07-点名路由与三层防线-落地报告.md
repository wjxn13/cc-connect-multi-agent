## 一、要解决的问题

`docs/05` 已经测清楚：**入站是扇出，不是路由**。一条微信消息会被原样投给配置里的每一个 project。

`docs/06` 的 L2 把代价压掉了一大半——「点名了别人」的消息不再进入模型。但有三类漏网：

1. **没有点名任何人的消息**。它不属于任何人，于是被投给所有人（L2 只拦「点了别人」，不拦「没点人」）。
2. **斜杠命令**。L2 与 L1 都对其放行（原因见第五节的豁免口）。
3. **图片**。微信没法在一条消息里同时发文字和图片，所以「@dsh」和图片**必然分两条到达**。
   第二条不含任何点名信息，看起来就是一条「没点人」的消息——而它实际上是有明确归属的。

再加上一个纯粹的用户体验问题：三个 agent 共用同一个微信窗口，**回复里看不出是谁答的**。
出错时尤其致命——报错说「会话启动失败」，但不说**谁的**会话失败了。

## 二、L1：引擎层点名关卡

### 2.1 判定规则

关卡**先看句首有没有连着写多个 `@`**（多播，2026-09-20 起），否则读**消息里第一个 `@` 记号**：

| 消息形态 | 判定 | 结果 |
|---|---|---|
| **句首连着写多个 `@`**（名字之间只有空格 / `,` `，` / `、` / `;` `；` / `+`） | **段内每个被点名的 project 都放行** | **多播：点名几个，几个就答**（详见 2.5） |
| 第一个 `@` 指向**别的** project | 丢弃（drop） | 该消息不进入本 project，**零会话、零进程、零 token** |
| 第一个 `@` 指向**自己** | 放行 | 进入本 project |
| 没有 `@`（或 `@` 的名字不在别名表里） | **看本 project 的 `default`** | `default = "answer"` → 放行；**`default = "silent"` → 丢弃**（同为零 token） |

⚠️ **最后一行是极易记错的一点**（2026-09-20 实测更正）。`default = "silent"` 的项目在**无点名**时
是被 L1 **直接丢弃**的，**不是「先跑一遍再由 L3 静默」**。代码在 `core/engine.go` 的
`mentionGateTargets()` 末尾：

```go
// The message mentions nobody we know.
if fallback == "silent" {
    return []string{mentionUnaddressed}, nil, false // → drop，日志记 addressed=(unaddressed)
}
return nil, nil, false                              // → 放行
```

⇒ 所以在「无点名」这条路径上，silent 的项目**根本不消耗 token，L3 也不会被触发**；
L3 真正要兜的是**斜杠命令**与**answer 项目撞上别名盲区**这两类（见 5.3）。
本机 `core/mention_route_test.go` 对 `mentionGateDrop("随便聊聊") == mentionUnaddressed`
有专门断言 —— 这是**有意为之且有测试覆盖**的行为，不是漏判。

放在引擎里而不是 agent 里的直接收益：**关卡命中时连会话都不会被创建**。
L2 虽然也省掉了模型调用，但 agent 进程已经起来了、消息已经跑完钩子链路。

### 2.2 别名归一化（否则「@DSH」和「@dsh」是两个人）

`NormalizeMentionAlias` 统一折叠：**大小写**、**首尾空白**、**前导 `@` 可省**。
于是 `@DSH`、` @dsh `、`dsh` 是**同一个记号**。

匹配用**最长别名前缀**而非首次命中，避免一个短别名把以它为前缀的长别名遮住
（例如同时登记了 `@d` 和 `@dsh` 时，`@dsh` 必须判给 `@dsh`）。

### 2.3 配置校验（把错配挡在启动时）

`validateMentionAgents` 在配置加载阶段就拒绝以下情况，而不是等运行时出现诡异路由：

- `project` 缺失，或**不对应任何 `[[projects]]` 的名字**；
- 同一个 `project` 被声明**两次**；
- 同一个别名被**两个 project** 同时认领（不报错就会两边都放行或两边都丢弃，行为不可预期）；
- 条目里**没有一个可用别名**（等于配了却永远匹配不上）；
- `default` 不是 `answer` / `silent`。

### 2.4 webhook 入口也要过关卡

webhook 是**绕过 `handleMessage` 直接往处理循环里塞合成消息**的，所以它在
`executePrompt` 的开头单独调了一次关卡。漏掉这一处，webhook 就成了关卡的旁路。

### 2.5 多点名广播（2026-09-20）

**动机**：用户要「一条消息点名几个 agent，几个就都回答」。在此之前，「第一个赢」的位置判定下
`@wb @dsh 看下这个` 只有 wb 会答，dsh 收不到。

**语义（用户拍板，别自行改）**：

1. **只有句首连着写才多播。** `@claude 帮我叫 @dsh 干活` 里的 `@dsh` 在句首段**之外**，
   不参与判定。句中提名远多于句中点名；若改成「全句集合判定」，这类消息会让两家**同时沉默**，
   那是所有失败模式里最坏的一种。
2. **粘性记全部被点名的。** `@wb @dsh 看下这张图` 之后**单独**发的那张图，同时归 wb 和 dsh。

**算法**（`core/engine.go`）：先用 `scanLeadingMentionRun` 取句首连续段 —— 跳前导分隔符、
必须以 `@` 开头、循环「读 `@name` → 跳分隔符」，遇到「既不是分隔符也不是 `@`」的字符即结束。
段非空时，段内每个命中别名的 token 都进 `owners`（去重、保序）；段为空才退回「第一个命中者赢」。
**分隔符白名单**（`isMentionSeparator`）= ASCII 空白、`U+00A0`、`U+3000`、`,`、`U+FF0C`、
`U+3001`（顿号）、`;`、`U+FF1B`、`+`、`&`。
裸 `@` 会**终止**整段（不是跳过），所以 `@ @dsh` 之后只剩 `@dsh`。

**实现要点**：

| 文件 | 改动 |
|---|---|
| `core/mention_sticky.go` | `Mark` 收可变参数、去重、**替换而非合并**（后一条单点名要把上一条的多点名单收窄，否则图会继续扇给已经不再说话的对象）；`Lookup` 返回 `[]string` **副本** |
| `core/engine.go` | 新增 `mentionGateTargets`（返回一组 owner + 一组 token + 是否含自己）、`scanLeadingMentionRun`、`isMentionSeparator`；旧入口 `mentionGateDrop` 降为**薄包装**（`strings.Join` 成 `"a,b"`），既有测试与日志格式不受影响；`mentionGateBlocked` 的 `addressed` 字段改为可容多值；`mentionsSelf` 改为**委托** `mentionGateTargets`，从结构上保证「粘性标记」与「关卡」不可能分歧 |

**⭐ 只改 L1 是不够的（本次的实际教训）**：L1 放行之后，消息进入 agent，还要过 **L3 的规则文字**。
四个规则文件当时写的是「正文点名了别的 agent 就 `NO_REPLY`（出现在句首或句中都一样）」，
于是 `@claude @dsh 谁写得对` 虽被 L1 放行给两家，**两家都会回 `NO_REPLY` → 一起沉默**，
用户什么也收不到。规则必须与关卡判定对齐，统一改成「**句首点名段**」写法：段里有我 →
去掉整段点名前缀后正常作答（**段里还有别人也要答**）；段里有别人、没有我 → `NO_REPLY`；
**段之外的 `@名字` 不参与判定**（那是句中提及，不是让你闭嘴）。
涉及四个文件：`config.toml` 的 `append_system_prompt`、`C:\Users\86180\AGENTS.md`、
`wb-agent` 的 `AGENTS.md` 与 `CLAUDE.md`（后两份内容相同，**都要改**）。

**测试**：新增 `TestMentionGate_LeadingRunWins`、`_LeadingRunSeparators`、`_LeadingRunBroadcasts`
（最后一个是 cluster 级 —— 每个 engine 只看得到自己的别名表，「大家都答了」只有在这一层才可观测）、
`TestMentionSticky_MarkHoldsASet`、`TestBarePhoto_MultipleAddresseesAllReceiveIt`；
并把 `TestMentionsSelf_MatchesGateRule` 里的 `{"@dsh @claude 是谁", false}` 改成 `true`
（句首段里包含自己就该答，这是本次语义变更的直接后果）。

**⭐ 还有第三处要同步：L2 钩子（端到端实测踩到，第三轮才修好）**

点名判定其实散落在**三个**地方，改一个不改另一个就会出现「一边放行、一边拦截」：

| 层 | 实现 | 多播上线后是否要改 |
|---|---|---|
| **L1 引擎** | `core/engine.go` `mentionGateTargets` | ✅ 本次改的就是它 |
| **L2 钩子** | `~/.cc-connect/hooks/l2-userpromptsubmit.js` | ✅ **也要改**（它有自己的行首锚定正则） |
| **L3 规则文字** | `config.toml` 的 `append_system_prompt` ＋ 3 个 `AGENTS.md`/`CLAUDE.md` | ✅ 也要改 |

L2 的症状很隐蔽：L1 日志显示消息**已放行**、agent 也报了 `turn complete`，
但 `silent=true`，微信侧什么都没收到。铁证在 `logs/l2-hook.jsonl`：
`{"agent":"dsh","targetOther":true,"block":true,"namedAgent":"@claude"}` ——
旧正则 `/^@(claude|...)/` 锚定行首，`@claude，@dsh，…` 对 DSH 来说行首是 `@claude`，于是被拦在模型之前。
**开全新会话（`/new`）也没用**，因为根因不在会话上下文，在钩子（本轮排查先错判成「ACP resume 不重读 AGENTS.md」，
被 `/new` 后复现静默证伪）。

钩子已重写为调用 `scanLeadingMentionRun`（与引擎同一套分隔符白名单），离线喂 stdin **12/12 通过**；
钩子是**每条消息重新加载**的，改完即生效、无需重启服务。

**端到端最终结果（2026-09-20 11:49，真人微信发 `@claude，@dsh，此消息为测试信息…`）**：
`my-workbuddy` 被 L1 drop（`addressed=my-project,my-dsh token=@claude,@dsh`）；
`my-dsh`（ACP）与 `my-project`（claudecode）**都**返回 `silent=false` 并真的投递到微信；
`l2-hook.jsonl` 记 `run=['claude','dsh'] block=False`。**多播链路贯通**。

> 附带确认一条独立机制：**DSH 的 ACP 会话 `is_resume=true` 时不会重读 `AGENTS.md`** ——
> 所以改 DSH 的 L3 规则文字后仍需 `/new`；这与上面的 L2 问题是**两件事**，都要做。

## 三、粘性点名：让图片跟上它的主人

### 3.1 微信侧三种「想同时发文字和图片」的实测（全部失败）

| 尝试 | 结果 |
|---|---|
| 图片预览页直接输入文字 | **预览页底部没有输入框**，物理上做不到 |
| 引用图片 + 发文字 | 文字到了，**图片被丢掉** |
| 引用文字 + 发图片 | 图片到了，**引用被丢掉** |

→ 结论：**“@dsh 看这个” + 图片，永远只能是两条消息**，其中第二条不含任何归属信息。

### 3.2 设计

一条**被点名**的消息会刷新一个短时效的「当前说话对象」（`core/mention_sticky.go`），
随后到达的**无文字消息**（也就是图片）就按这个对象投递，而不是落到平台默认项目。

四个刻意的约束：

1. **只对无文字消息生效**。文字消息永远走 2.1 的正常判定，粘性不参与——
   否则「@dsh 问一句，再发一句给别人的话」会被错误地拉去 dsh。
2. **由媒体路由器消费，不由关卡消费**。关卡该丢还是丢，粘性是**路由**信息，不是**门禁**信息。
3. **TTL 3 分钟，且刻意短**。足够覆盖「先打 @dsh、再去挑图片」；
   短到「人走开了、几分钟后随手发张图」不会静默地被送给一个早已忘记点过的对象。
4. **记的是一组 project，不是一个**（2026-09-20 随多点名一起改）。句首连续点名可以一次
   点几家，那张图就同时归几家 —— 若仍只记第一个，图会到 wb 而对 dsh **静默消失**，
   等于把 3.1 那个 bug 换个形态重演一遍。相应地 `Mark` 是**替换**语义而非合并：
   后一条单点名消息要能把多点名的集合收窄。

### 3.3 端到端证据（2026-09-19 22:03，先 `@dsh` 再单独发图）

```
mention gate: media message kept    project=my-dsh        owner=my-dsh
mention gate: media message dropped project=my-workbuddy token=(media)
mention gate: media message dropped project=my-project   token=(media)
```

三条投递里**只有 dsh 留下**，另两条按 `token=(media)` 记录在案。
同一批次的**文字**消息路由正常，说明粘性没有污染文字通道。

## 四、出站身份：让同一窗口里的三个 agent 可分辨

`agent_label`（全局，放在 `[display]` 下）与 `label`（每个 project 自己的显示名）共同渲染出站前缀。
**project 级覆盖全局级**；两者都没配则不加前缀。

施加点在**引擎的两个发送咽喉**，而不是散落在各个调用处——否则漏一处就会出现「大部分回复有标识、
某一类通知没有」的诡异现象。长文本被平台切成多条时**只有第一块带前缀**（微信会切），这是刻意的：
标识的作用是「我是谁」，不需要每条重复。

顺带修掉了三处**在共用一个账号时才暴露出来的**文案缺陷：

| 键 | 原来 | 现在 |
|---|---|---|
| `MsgMessageQueuedDetail` | 只说「已排队」 | 补上**第几位**、**谁在占用**、**将由谁执行** |
| `MsgMessageQueuedReroute` | 无 | 告诉用户**怎么改派**给别的 agent（有 peer 时才出现） |
| `MsgFailedToStartSessionWhom` | 只说会话启动失败 | 点名**是哪个 project 失败**，并给出 `/stop` / `/new` 的恢复路径 |

三个键都补齐了文件里既有的五种语言。

## 五、三层防线是叠加的，不是替换的

这是本轮最容易理解错的一点。**L1 落地后 L2 并没有被取代，L3 也没有被取代**——各自还在挡不同的东西。

### 5.1 L2 仍在运行，只是被 L1 抢了大部分活

`hooks/l2-userpromptsubmit.js` 的拦截统计：

| 范围 | 拦截条数 |
|---|---|
| 全部历史 | **121** |
| 本轮当天 | **2**（`15:11:12` dsh ← `@claude，你好`；`19:54:35` dsh ← `@wb 自愈验证…`） |

而这 2 条都发生在 **L1 覆盖 my-dsh（20:13）之前**。此后同类消息**在进入 DSH 进程之前就被 L1 丢掉了**，
根本没有机会到达 L2——所以日志里 L2 的拦截数不再增长，是**正常的**，不是钩子失效。

对照证据：同一时段的桥接日志出现
`mention gate: message dropped project=my-dsh addressed=my-workbuddy token=@wb`，
即该消息被 L1 拦在了入口。

### 5.2 `requireGate` 不是「失效」，是**故意**为 `false`

钩子脚本里每个平台的 `requireGate` 取值不同，这一度让人误判为配置漏了：

| 平台 | `requireGate` | 原因 |
|---|---|---|
| `claudecode` | **`true`** | 钩子挂在**全局** `~/.claude/settings.json`，不门控就会拦用户自己开的会话 |
| `workbuddy` / `dsh` | **`false`** | 钩子**只注入给桥接进程**，天然隔离；再加门控反而会因为环境变量漏配而**静默失效** |

→ 所以启动探针里打出 `gated=False` **不代表配错了**。
⇒ 推论：`CC_BRIDGE_L2=1` **只配在需要门控的那个 project 的 env 里**就是对的。

### 5.3 L3 为什么仍然必须存在

至少三个口子 L1 挡不住：

1. **斜杠命令豁免口（最主要）**。L1 对以 `/` 开头的消息**一律放行**（对所有 project 都放），
   而 cc-connect 遇到**未识别**的斜杠命令会 `fall through to agent as normal message`。
   ⇒ 这种消息会进入**全部** agent。

   ⚠️ **2026-09-20 实测更正**：这里原先写「只能靠 L3 让模型自己闭嘴」——**实测是不成立的**。
   发一条未注册的 `/xyz`，结果 `turn complete` **3 次**、`silent=false` **3 次**，
   **微信侧真收到三条回复**。原因是三个 agent 的点名规则里都写着
   「消息没有任何 `@` 前缀 → **正常作答**」——`/xyz` 没有点名，于是三家都照规则作答。

   ⇒ 结论要改写为：**L3 在斜杠命令这条路径上兜不住，缺的是规则不是机制**。
   要堵这个口子，要么给每个 agent 的规则补一条针对 `/` 开头的条款（纯配置，
   语义与 `default` 对齐：只有 `default="answer"` 的那个作答），
   要么收紧 L1 的豁免（见第六节，需改引擎重编译）。
2. **别名表盲区**。L1 按 `[[mention_agents]]` 登记的别名认人；写了别名表里没有的名字（如 `@gemini`），
   L1 只会把它当作「谁也没点名」——于是 silent 项目被丢、而 **answer 项目照答**，
   可用户其实是在叫别人。这种情况只能靠 L3 让 answer 项目自己克制。
3. **安全网**。配置写错、别名漏写、将来新增了某个入口却忘了挂关卡——L3 是最后一道兜底。

### 5.4 三层的成本对比

| 层 | 判定时机 | 拦下一条消息的成本 | 覆盖范围 |
|---|---|---|---|
| **L1** | 进 agent 之前 | **0 token**，连进程都不起 | 项目间点名 + **silent 项目的无点名消息**（均不含斜杠命令） |
| **L2** | 调用模型之前 | 0 token，但 agent 进程已启动 | 同样不含斜杠命令；依赖各平台钩子机制 |
| **L3** | 模型跑完之后 | **一次完整模型调用** | 全部（含斜杠命令、别名盲区） |

> 一句话：**L1 省钱、L2 兜住「进 agent 但不该跑模型」、L3 兜住「L1L2 都看不见的」**。
> 三者去掉任何一层，都会有一类消息退化回去。

## 六、已知边界（本轮没有解决）

- **斜杠命令仍会扇出**。当前策略是「`/` 开头一律豁免」，因为要在关卡里判断
  「这个命令是不是本 project 注册过的」需要额外一张清单。收紧它需要改引擎并重新编译，
  属于未竟项；在收紧之前，斜杠命令的防串扰**完全依赖 L3**。
- **粘性只覆盖图片**。它是「无文字消息」的通路；平台上其它无文字的媒体类型是否走同一条路径，
  本轮只验证了图片。
- **别名表是手工维护的**。新增 project 或改别名后，L1 的认知与 `[[mention_agents]]` 的一致性
  靠人保证（配置校验只能保证表内自洽，不能保证跟现实一致）。

## 七、维护警告：换模型后必须复查 L3

L3 依赖 agent 侧的**提示词约定**（让它在不该答时输出 `NO_REPLY`）。
**换模型后这个约定可能失效**——新模型未必遵守同样的静默指令，最坏情况是开始抢答。

复查方法：故意发一条「只 @ 了别人」的消息，看被豁免进入的那些 agent 是否仍然保持沉默。
若开始抢答，先回滚对应的模型改动，再评估是否需要补提示词。

> 相关：`docs/08` 记录了一次**模型路由修正**。那次修正同时改动了 agent 实际使用的模型，
> 因此**必须重跑本节这条复查**。
