# L2 前置拦截：把「不该我答」拦在模型调用之前

> 测试时间：2026-09-15 19:00 —— 2026-09-16 23:10
> 测试目的：让「点名了别的 agent」的消息**不进入模型**，而不仅仅是不发出来
> 结论：**三家平台全部落地并端到端验证通过**；其中 DSH 的实现推翻了两条来自官方文档/源码直读的结论
> 关联：`hooks/`（钩子与配置样例）、`patches/`（cc-connect 引擎侧补丁）、`docs/05-能力边界实测.md`（为什么需要它）

---

## 一、要解决的问题

`docs/05` 已经测清楚一件事：**入站是扇出，不是路由**。一条微信消息会被原样投给配置里的每一个
project，而「只有目标 agent 应答」靠的是 agent 侧输出 `NO_REPLY` 这个**提示词约定**。

代价是明确记录在案的：

> 每条用户消息 = **N 次完整 LLM 调用**（N = 挂微信的 project 数）
> 静默机制只挡住「消息位」，**挡不住 token 消耗**

三个 agent 共用同一个微信入口时，用户跟其中一个说话，另外两个**照样烧钱跑完一整轮**。

L2 的目标就是把这个代价降掉：**在模型被调用之前**就判定「这条不是给我的」，直接结束这一轮。

```
现状（L1）：消息 → agent → 模型跑完 → 输出 NO_REPLY → 桥接静默      ← 钱已经花了
目标（L2）：消息 → agent → 前置钩子判定 → 不是给我的 → 结束          ← 零 LLM 调用
```

> 📌 **编号注记（后续文档引入）**：本文写作时只有**两道**防线，所以把「输出静默」叫 L1、
> 把「前置钩子」叫 L2。之后在两者**之外**又加了一层**引擎层点名关卡**（它比前置钩子更早执行，
> 在**进入 agent 之前**就判定），于是三道防线按**执行顺序**重新编号：
>
> **L1 引擎层关卡**（当时不存在）· **L2 前置钩子**（= 本文的 L2，**含义不变**）·
> **L3 输出静默**（= 本文的 L1）
>
> 就此约定：**L2 这个名字在两份文档里指同一个东西**，只有原来的 L1 因为新层插到更外层而改称 L3。
> 本文正文未逐字回改（它是当时的现场记录），以 `docs/07-点名路由与三层防线-落地报告.md` 第〇节的编号为准。

## 二、钩子装在哪，为什么只能这么装

cc-connect **自己不管路由**（入站是扇出，`docs/05` 有完整证据），所以前置拦截**只能在每个 agent
自己的钩子层做**。三家的钩子机制都叫 `UserPromptSubmit`，但**挂载方式完全不同**：

| project | agent | 挂载位置 | 生效范围 |
|---|---|---|---|
| `my-project` | Claude Code | 独立 settings 文件 + `CLAUDE_CONFIG_DIR`，或全局 settings + 环境变量门控 | 需门控（全局 settings 若不门控，用户自己开的会话也会被拦） |
| `my-workbuddy` | WorkBuddy（ACP） | 在 cc-connect 的 `args` 追加 `--settings <file>` | **只作用于桥接进程**，天然隔离 |
| `my-dsh` | DSH（ACP） | `~/.dsh/profiles/acp/cordis.patch.yml` 加 `- insert:` 插件 | **只作用于 `--profile acp`**，web / tui 不受影响 |

> 细节与可复制的配置样例见 `hooks/README.md`，此处不重复。

一个进程级的**硬约束**（三家共通）：钩子脚本**必须按平台分支**。同一个脚本要同时服务三家，
靠 `--agent <平台名>` 或环境变量 `CC_BRIDGE_AGENT` 选定「我方是哪家」。

## 三、三家的阻断协议（实测，不是抄文档）

这是本次最反直觉的部分：**三家的「有效阻断写法」几乎没有交集**，而官方文档在两家上都把人带偏了。

| 平台 | 有效阻断写法 | 无效写法 | 证据等级 |
|---|---|---|---|
| Claude Code | stdout `{"decision":"block"}` 或 `{"continue":false}`，`exit 0` | **`exit 2` 无效**（与官方文档不符） | 假 API 四组对照，阻断时请求数 = 0 |
| WorkBuddy | 上述两者 **以及 `exit 2`** 三者都认 | —— | 二进制符号表 + 端到端 |
| DSH | stdout **仅** `{"decision":"block"}`，`exit 0` | `exit 2`（Windows 上失效）、`{"continue":false}`（完全不阻断） | 端到端 + 读会话 `hook/result` 事件 |

**Claude Code 侧的取证方法**（可复现，判据是「假服务器收到的请求数」，不是「有没有报错」）：

```bash
# 起一个假 Anthropic API，把每个请求追加到 req-log.jsonl
node mock-api.js
# 用独立 settings 注入钩子（不碰生产配置）
claude -p "@dsh 测试" --settings settings-variant.json
# 看 req-log.jsonl 有没有新增 POST /v1/messages
#   0 条 = 阻断成功；1 条 = 没拦住
```

> Claude Code 的官方文档写明「以 `exit(2)` 阻断」，但 2.1.270 的 `-p` 模式下实测：**钩子跑了、
> 请求照样发出**。唯一有效的是 stdout 里的 JSON。这条如果不实测，会得到「看起来配好了、
> 实际一直在烧钱」的假象。

## 四、DSH 的三个陷阱（全部推翻了「读文档/读源码」的结论）

DSH 侧是本次唯一**必须实机试错**才能做对的地方。

### 陷阱一：`exit 2` 在 Windows 上会被 PowerShell 改写成 `1`（决定性）

官方协议确实把 `exit 2` 定义为阻断码：

```js
// @deepseek-ai/dsh-hook-protocol/lib/index.js
const BLOCKING_EXIT_CODE = 2
if (exitCode === BLOCKING_EXIT_CODE) {
  output.decision = "block"
  if (stderr) output.reason = stderr.trim()
}
// rank("block") = 3 → mergeHookOutputs() → decisionForRank(3) = "deny"
// 插件 @deepseek-ai/dsh-hooks-claude-code 的 agent/pre-step：
//   if (merged.decision === "deny") return { kind: "reject" };   // 模型不跑
```

**但它在 Windows 上跑不通。** 根因：DSH 的 `ctx.shell` 在 Windows 上走 **PowerShell**
（`dsh-shell` 源码注释原话：`"the win32 layer swaps the POSIX rows for the pwsh ones"`），
而 PowerShell 执行**原生**命令时，子进程**只要往 stderr 写东西**就触发 `NativeCommandError`
→ **把退出码改写成 `1`**。

实测（读 DSH 会话记录里的 `hook/result` 事件）：

```json
{"decision":"pass","exitCode":1,"stderrSummary":"NO_REPLY"}
```

→ 退出码不是 2 就**不是阻断**，模型照跑。日志上钩子「跑了」，却完全没拦住。

**正解**：改用 **stdout JSON**（走 `exit 0`，PowerShell 不介入退出码）：

```json
{"decision":"block","reason":"NO_REPLY"}
```

协议依据：`parseHookOutput` 在 `exitCode === 0` 且 stdout 以 `{` 开头时才解析；
`topLevelDecisionOf` 接受顶层 `"approve"` / **`"block"`**（**不接受** `"deny"`）。

### 陷阱二：`{"continue":false}` 在 DSH 上根本不阻断

插件 `agent/pre-step` **只检查** `merged.decision === "deny"`。
`continue:false` 只置 `stop`（那是 `Stop` 事件用的）→ 写了也不会阻断。
所以 DSH 的 response 与 Claude Code 同构，都是 `{decision:'block', reason:'NO_REPLY'}`。

### 陷阱三：hook 命令里**不能带引号**

DSH 执行 hook 时会自行加前缀，且**不做 shell 层面的引号转义** →
`"C:/…/node.exe"` 被 PowerShell 当作字符串字面量，报：

```
表达式或语句中包含意外的标记"C:/…/l2-userpromptsubmit.js"
```

→ 本机两条路径都无空格，**裸写**即可。若路径含空格，需要另想办法（这是 DSH 的一个真实限制）。

> 对照：**WorkBuddy 那份配置反而必须带引号**。两份 JSON 只差引号，但都是硬要求 ——
> 所以它们不能共用同一个文件。

## 五、一个真实的假阳性（最容易误判为成功）

DSH 钩子**第一次跑的时候完全没执行**，但现象看起来是「成功」：

| 观测项 | 读数 | 误判 |
|---|---|---|
| `tools=` | `0` | 「没调工具，说明被拦了」 |
| `response_len=` | `8` | 「正好是 `NO_REPLY` 的长度，对上了」 |
| `silent=` | `true` | 「静默生效了」 |

**实际上**：钩子压根没运行（钩子日志里 `agent=dsh` 的计数为 0），那 8 个字节是
**模型自己输出的**。反证是耗时 —— 那一轮 `turn_duration=12 秒`，而真正被拦的轮次应在 1 秒内。

**结论：唯一可靠的判据是读 agent 侧的会话记录，不是 cc-connect 的单行日志。**

- DSH：解 `sessions/*.jsonl.zstd`，看 `hook/result` 事件（`{exitCode, decision, stderrSummary, durationMs}`）
  与同轮 `request/header` 的条数。`request/header = 0` 才是「模型真没被调用」的铁证。
- cc-connect 的 `tools=` / `turn_duration` 只能当**旁证**。

## 六、引擎侧需要两处补丁（否则拦住了也会漏内容给用户）

`hooks/` 里的拦截做得越准，就越频繁地出现一种情况：**这一轮 agent 什么正文都没有**。
cc-connect 的 ACP 适配器**不解析** `turn/end` 的 `{kind:"blocked"}`（全仓搜
`stopReason|blocked|refusal` 在 `agent/acp/` 下**零命中**），于是「无正文」的回合会露出破绽。

**「无正文」有两种形态，成因不同、出现在不同平台，各需要一处补丁：**

| 形态 | 谁会产生 | 现象 | 补丁 |
|---|---|---|---|
| agent **吐了文本**，但文本是钩子阻断的包装 | Claude Code（留下 `HookBlockedError` 文本） | 包装文本被当回复投递，且**会被携带到下一轮**、与真回复直接粘连 | `patches/0005` |
| agent **一个字都没吐** | DSH / ACP（`{kind:"reject"}` 真·零输出） | 落到 `MsgEmptyResponse` 占位符 `(空响应)` 并被投递 | `patches/0006` |

### 第一处补丁的策略演变（值得记一笔）

初版策略是「**检测到阻断文本 → 整条静默**」。它有个致命缺陷：
阻断文本会**被携带到下一轮**、与下一轮的真回复粘连成一条，于是「整条静默」会把
**那一轮的真回复一起吞掉** —— 用户看到的现象是「**每拦一次，我下一条消息就没回**」。

改成「**剥离包装、只投递剩下的真回复**」后，三场景实测 3/3：

| 场景 | 实测长度 | 期望 |
|---|---|---|
| A 纯阻断（没有真回复） | 35 字节 | 静默 |
| B 包装 + 真回复粘连 | **46 字节** | **投递**（未剥离应为 81 字节，差 35 = 包装长度） |
| C 干净轮 | 37 字节 | 正常投递 |

### 第二处补丁的判据

「空响应」这个占位符**恰恰是点名制正常工作的必然产物** —— 拦得越准，越常出现。
它对用户零信息价值，所以直接静默；而真正的 agent 故障走 `EventError` 分支，不受影响。

完整补丁说明与「怎么往上提」见 `patches/README.md`。

## 七、端到端验证证据

测试通道：`cc-connect cron exec -p <project>` —— 已实测**不扇出**，
只注入指定 project 的一个会话，其余两个完全不动（最干净的隔离通道，且不刷用户微信）。

### DSH（`my-dsh`）

| 场景 | 钩子读数 | 模型调用 | 轮次结束 | cc-connect 侧 |
|---|---|---|---|---|
| A′ 点名 `@claude`（应拦） | `{decision:"block", exitCode:0}` | **`request/header` = 0 条** | `turn/end {kind:"blocked"}` | `empty response suppressed` + `silent=true` |
| B′ 点名 `@dsh` 自己（应放行） | `block:false` | 正常 | 正常 | `tools=2`、`response_len=50`、`silent=false` |

- 被拦轮次耗时 **925 毫秒**，对比正常轮 5–15 秒（Claude Code 正常轮可达 15–64 秒）
  → **真·零成本**的量级确认，不是「省了点」。
- B′ 证明**不误伤**：该自己答的时候照常答。

### 三家共同的旁证

拦截记录落在 `~/.cc-connect/logs/l2-hook.jsonl`（钩子自己写的一份结构化日志）：

```json
{"ts":"…","agent":"dsh","gated":true,"required":false,
 "targetOther":true,"block":true,"namedAgent":"@claude",
 "promptHead":"@claude 帮我看看","matchHead":"@claude 帮我看看",
 "cwd":"…","sessionId":"…"}
```

其中 `sessionId` 能与 cc-connect 主日志 `turn complete` 的 `agent_session` **对上号**
（本机实测两边同为 `4f6445ba-…`）→ 闭环证明「这个钩子确实介入了这一轮」，
而不是「配了但没被调用」。

## 八、一个隐蔽的漏拦：`<system-reminder>` 前缀

点名判定是**开头锚定**的（`^@xxx`）。而 DSH 同一会话的**后续消息**，
`payload.prompt` 有时会带上工作区指令注入块：

```
<system-reminder>
The following workspace instructions may b…
</system-reminder>
@claude 帮我看看
```

→ 注入块挡在前面，正则匹配不上，**钩子放行** → 模型真的跑 → token 白花。

这条之所以隐蔽：**agent 侧的 `NO_REPLY` 约定仍会兜底**，所以在微信里看不到任何异常，
只有 `l2-hook.jsonl` 里能看出这一轮没被拦。

修法：`stripLeadingSystemReminder()` —— 只剥**开头**的块（可连续多段），
正文中间出现的标签**不动**（避免误伤正常内容）。日志因此新增 `matchHead` 字段：
**`promptHead` ≠ `matchHead` 就说明命中了这条**。

## 九、回归测试：31 例，离线，不花 token

```bash
python scripts/l2_hook_tests.py     # 期望末行：结果：31/31 通过
```

覆盖 **claudecode 8 例 / workbuddy 8 例 / dsh 12 例 / 命令行传参 3 例**，
全部直接喂 JSON 到钩子的 stdin，**不启动任何 agent**。

它钉死的是几条**最容易被后续改动悄悄破坏**的约定：

1. `reason` 必须**恰好**是 `NO_REPLY`（WorkBuddy / DSH）—— 多一个字就会被当正文投递到微信；
2. 拦截理由里要写**实际**被点名的那个 agent（曾经硬编码 `@dsh`，拦 `@wb` 时理由也说 `@dsh`，
   排查时被带偏）；
3. 负向先行断言 `(?![a-z0-9_])`：`@dshx` 不算点名（否则前缀相似的词会被误伤）；
4. `stripLeadingSystemReminder()`：带注入块前缀**仍要能拦**，正文中间出现则**不得误伤**。

## 十、维护警告与已知边界

### 必须记住的四条

1. **npm 升级会覆盖 `bin/cc-connect.exe`** → 本仓库的补丁全部丢失，需要重新编译部署。
2. 编译**绝不能加** `-tags no_web` —— 那会把 Web 管理后台整个丢掉。
   自检：`grep -ac "index.html\|favicon.svg" cc-connect.exe`，新旧二进制应一致（本机 = 6）。
3. 换模型 / 重写 agent 的 settings 文件，会**冲掉 `hooks.UserPromptSubmit`**。
   自检：钩子日志里对应平台的记录数为 0 就是没了。
4. 换了 agent 的**启动方式**（改 args、改 profile）后要重新确认钩子还在。

### 边界（本轮没有解决）

- **`relay` 路径打不到钩子**。agent 之间互相拨号走的是 `HandleRelay` 独立路径、
  不套静默判定 —— 前置拦截对它无效，拿到的仍是未清洗原文。
- **成本是 O(N²)**：多接一个 agent 就多一处待验、多一个平台分支。
  目前 N=3；再加人要把这一整套重做一遍。
- **版本基线**：本仓库补丁的基线是 **v1.3.4**，而核对时上游已是 **v1.5.0**
  （`main` 最新提交 2026-09-10）。补丁对上游 `main` 仍能干净应用（已验证），
  但本机跑的桥接确实落后上游两个小版本。

### 截至核对时（2026-09-16）上游仍未修

```bash
git grep -n "MsgEmptyResponse" FETCH_HEAD -- '*.go'
# → core/engine.go:5767  全仓仅此一处调用，且是**无条件赋值**

git grep -niE "hookBlocked|prevent_continuation|blocked by hook" FETCH_HEAD -- '*.go'
# → 空

git grep -niE "stopReason|blocked|refusal" FETCH_HEAD -- 'agent/acp/*'
# → 空
```

→ 本仓库的补丁**依然有效、尚未上游化**。是否提 PR 见 `patches/README.md` 末尾的建议。

## 十一、结论

| 平台 | 前置拦截 | 模型调用 | 端到端验证 |
|---|---|---|---|
| Claude Code（`my-project`） | ✅ | 0 次（假 API 请求计数为证） | ✅ |
| WorkBuddy（`my-workbuddy`） | ✅ | 0 次 | ✅ |
| DSH（`my-dsh`） | ✅ | 0 次（同轮 `request/header` = 0 条） | ✅ |

**至此，点名制不再依赖模型自觉** —— 三家都在模型被调用之前就做完了判定。
`NO_REPLY` 仍然保留，但它的角色从「唯一的静默手段」降级为「兜底」。
