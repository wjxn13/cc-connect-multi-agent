## 二、真正的根因

### 2.1 cc-connect 的 ACP 适配器不区分「思考块」和「正文块」

排查方式：直接在 cc-connect 程序里搜索协议关键字。

| 搜索的关键字 | 命中次数 |
|---|---|
| `agent_thought_chunk`（ACP 标准里的「思考块」类型） | **0 次** |
| `agent_message_chunk`（ACP 标准里的「正文块」类型） | 1 次 |

**它根本不认识"思考块"这个概念**，于是把思考块和正文块**都当成正文拼成了一条回复**。

### 2.2 但 agent 侧是完全规范的

我用新写的探针 `scripts/acp_dump.py` 直接连 DSH 抓取原始 ACP 消息：

```
[UPDATE] agent_thought_chunk | 'The message starts with "@claude，你好"...'
[UPDATE] agent_message_chunk | 'NO_REPLY'          ← 正文干净、独立
```

**思考和正文是干净分离的两条消息** —— 所以问题只在中间通道，不需要改动 agent 本身。

这也解释了为什么 `clean_reply` 没用：它按"剥离特定格式的进度行"设计，而这里是**自由文本被直接拼接进正文**。

# 第二部分：memorix 共享记忆层（2026-09-14 22:30）

> 微信桥接层跑通后，接着排查"agent 的 memorix 层没跑通"。

## 七、主因：memorix 拒绝把 $HOME 及其子目录当项目根

报错原文：

```
Error: Refusing to bind $HOME as a project root (C:/Users/<USER>).
Pass a git project via --cwd, MEMORIX_PROJECT_ROOT, or memorix_session_start({ projectRoot }).
```

而三个 agent 的 work_dir **全在 `$HOME` 下**：

| Agent | work_dir | 是否 $HOME 或其子目录 |
|---|---|---|
| Claude Code | `C:/Users/<USER>` | ✅ 就是 $HOME |
| DSH | `C:/Users/<USER>` | ✅ 就是 $HOME |
| 桥接 WorkBuddy | `C:/Users/<USER>/wb-agent` | ✅ $HOME 的子目录 |

→ 一个都绑不上项目。这就是"memorix 层没跑通"的**主因**。

**修法**：四端的 memorix 全部加 `--cwd D:/memorix-shared`（真实 git 仓库 `wjxn13/memorix-shared`，正是本机设计中的共享记忆载体）。生效后的启动日志：

```
[memorix] Project root: D:/memorix-shared
[memorix] MCP Server running on stdio (profile: lite, project: wjxn13/memorix-shared)
[memorix] Prepared search index for 276 observations in project: wjxn13/memorix-shared
[memorix] Tool profile: lite (core memory + sessions, 20 tools)
```

## 八、四端配置位置（本机实况）

| 端 | 配置位置 | 备注 |
|---|---|---|
| WorkBuddy 桌面版 | `~/.workbuddy/mcp.json` | `~/.workbuddy` 是指向 `D:/workbuddy/.workbuddy` 的符号链接 |
| Claude Code | `~/.claude.json` 顶层 `mcpServers` | 原为裸命令 `memorix` + 无 `--mode`（默认 `micro`，工具最少）→ 已改 node 绝对路径 + `--mode lite` |
| DSH | `~/.dsh/cordis.patch.yml`（全局，非 profile 专属） | insert 条目 id = `memory-memorix`；原样写的是裸命令，dsh 清理子进程环境后解析不到 → 必须绝对路径 |
| **桥接的 WorkBuddy**（CodeBuddy CLI） | **上面三份都不读** → 必须用 `--mcp-config` 显式传 | 见第九节 |

## 九、次因：桥接的 WorkBuddy 加载到的 MCP 数为 0

实测日志（`~/.codebuddy/logs/<日期>/wb-agent__*.log`）：

```
[Startup] McpConfigManager: total MCP servers from plugins: 0
[MCP] reconcile revision=0..5 projected (retained=0, pending=0, evicted=0)
```

它虽被识别为 WorkBuddy 产品，但 user 作用域**没读到**桌面版那份 `~/.workbuddy/mcp.json`。

**为什么确定 `--mcp-config` 这条路可行**：同一份日志里存在一次 `mcpConfig={"mcpServers":{}} strictMcpConfig=true` 的 ACP 启动，说明 **ACP 模式下 CLI 确实会解析 `--mcp-config` 并把条目投进 dynamic 作用域**（那次配置为空所以 retained=0）。传非空配置即可保留。

**修法**：在 cc-connect 的 `args` 里显式传（JSON 字符串；TOML 用单引号包裹 = 字面量，无需转义）：

```toml
args = ["...acp-thought-filter.js", "<node.exe>", "...codebuddy", "--acp", "--acp-transport", "stdio",
        "--mcp-config", '{"mcpServers":{"memorix":{"command":"<node.exe>","args":["D:/npm-global/node_modules/memorix/dist/cli/index.js","serve","--mode","lite","--cwd","D:/memorix-shared"]}}}']
```

顺带确认：cc-connect 二进制里**没有** `strict-mcp-config` 字样，所以日志里那次带 strict 的启动不是桥接发起的，不会覆盖我们的配置。

## 十、第三个坑：MCP server 是异步启动的（探针极易误判）

memorix 启动时要建索引（本项目 276 条 observations），实测需十几秒。若在 `session/new` 之后**立刻**发 prompt，工具列表里看不到 memorix，很容易误判成"配置没生效"——本次就先踩了一次，差点走错方向。
`scripts/acp_dump.py` 已内置 20 秒预热等待；cc-connect 实链路的 agent 是常驻的，第二条消息起不存在该问题。

## 十四、接着暴露出的新坑：agent 调工具时「权限挂起」

### 症状：微信里那条 @wb 完全没回复

对照三个 project 的会话记录：

| Project | history 尾部 |
|---|---|
| my-project（Claude） | `assistant :: NO_REPLY` ✅ |
| my-dsh（DSH） | `assistant :: NO_REPLY` ✅ |
| **my-workbuddy** | **`user :: @wb，你还记得我们上次聊的memorix吗？` ← 到此为止，没有 assistant** ❌ |

它的回合**永久挂起**了。日志特征：

```
level=INFO msg="acp: permission request" request_id=0 tool=permission input="{...search...}"
level=INFO msg="permission request" request_id=0 tool=permission
```
此后不再有该 project 的 `turn complete`。

### 根因

ACP 协议下 agent 执行工具前要向**客户端**发 `session/request_permission`。
cc-connect 虽然是客户端，但微信桥接是**无值守**的 —— 没人点「允许」，回合就永久挂起。
（二进制里确实有「允许/允许所有/拒绝」提示文案，但这次实链路没把审批卡发到微信，不能指望人工批准。）

### 修复（按你选的「全自动」）

**A. 桥接 WorkBuddy** —— 加 CLI 参数：

```toml
args = [..., "--acp", "--acp-transport", "stdio",
        "--permission-mode", "bypassPermissions",
        "--mcp-config", '{"mcpServers":{"memorix":{...}}}']
```

**B. DSH** —— 改 `~/.dsh/profiles/acp/cordis.patch.yml`（**只作用于桥接 profile**，你日常用的 web/tui 不受影响）：

```yaml
- id: sandbox-policy
  config: { mode: danger-full-access, workspaceRoot: !!js process.cwd() }
- id: user-approval
  config: { policy: never }
- id: permission                      # ← 少了这段 dsh 直接起不来
  config:
    presets: { read-only: {...}, workspace-write: {...}, danger-full-access: { sandbox: danger-full-access, approval: never } }
    defaultPreset: danger-full-access
```

**连环坑（值得记）**：只改前两项、不写第三项，dsh 启动即失败：

```
permission: composed sandbox and approval defaults match no preset; configure defaultPreset explicitly
```
表现是「握手成功、但 prompt 后收不到任何消息」——很像是网络问题，实际是配置问题。

**顺带修掉一个无关 bug**：原先 `workspace-write` 沙箱在本机启动就失败
（`Windows ACL temp root must be outside the workspace`），导致 DSH 的 shell 工具根本跑不起来。关沙箱后消失。

### 本地实测（新脚本 `scripts/acp_permission_probe.py`）

# 第五部分：微信收到「错误: [vdb-node] server ready …」的假报警（2026-09-14 23:00）

## 二十二、结论先说：正常，是我的重启副作用，已修好不会再发生

你没有提问，微信却收到一条以「错误」开头、内容是 MCP 服务启动横幅的长消息。
**这不是功能故障**，是我 22:56 重启 cc-connect 时杀掉 agent 进程的副作用。

## 二十三、根因（日志三行连读即可判定）

```
level=ERROR msg="acp: process exited" error="exit status 0xffffffff" stderr="[vdb-node] ..."
level=INFO  msg="unsolicited events detected, relaying to platform"
level=ERROR msg="unsolicited agent error" error="<同一大段 stderr>"
```

三步因果：

1. `exit status 0xffffffff` = 进程被**强制结束** —— 即我重启时杀掉了 DSH 的 agent。
2. agent 的 MCP 子进程（`vdb-node` 视频取证 / `argo-mcp` / `memorix`）启动横幅打在 **stderr**，
   而 `acp-thought-filter.js` 原本是 `child.stderr.pipe(process.stderr)` —— **原样透传**。
3. cc-connect 把这些 stderr 判定为 `unsolicited agent error`（未被请求的 agent 错误），
   **直接转发到微信**。

**为什么显得突兀**：stderr 平时是「静默攒着」的，**杀进程那一刻才被整段刷出去**。
所以用户视角是「我没问啊，怎么突然报错」。

## 二十四、修复：噪音只落档、不转发

在 `acp-thought-filter.js` 里把 stderr 从「透传」改为「判别后转发」：

```js
const NOISE_RE = new RegExp('^\\s*(' +
  '\\[vdb-node\\]|\\[argo-mcp\\]|\\[memorix\\]|\\[acp-thought-filter\\]' +
  '|\\(node://d+//)|//[UNDICI-EHPA//]|EnvHttpProxyAgent|ExperimentalWarning' +
  ')');
// 命中 → 只 append 到 ~/.cc-connect/logs/acp-agent-stderr.log
// 未命中 → 照常转发（真报错不能吞）
```

**为什么不做全量静默**：真正的报错（认证失败、插件加载失败）还得让 cc-connect 能报出来，
所以用**白名单式抑制噪音**；被抑制的行也**留档**（带时间戳），排查时照样看得到。
落档路径可用 `ACP_FILTER_STDERR_LOG` 覆盖。

## 二十六、顺带学到：重启顺序的两条规则会打架

| 目标 | 顺序 | 原因 |
|---|---|---|
| 避免微信收到假错误 | **先杀 cc-connect，再清残留子进程** | stderr 在「杀 agent」那刻才刷出；cc-connect 已死就没人转发 |
| 避免堆积孤儿进程 | 先子后父 | Windows 上父进程死后子进程不会跟着死 |

**兼顾写法**：先杀 cc-connect，隔 2 秒再杀残留后代。
或者**挑「没有 agent 在运行」的时机重启**——本次就是这样：重启后没有微信消息进来，
所以没有 agent 进程，新过滤器会在下一条消息到来时自然加载，**无需再重启**（正好避开又一条假错误）。
